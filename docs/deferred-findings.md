## Found while polishing (2026-11-22)

Still open; none of these blocks a push or loses a highlight. Deferred from the polish list itself: none.

- **A corrupt `batch.json` is invisible.** `BatchStore.list()` skips it (one warning per bad batch per process, then quiet debug logging), so the batch is hidden from the UI and neither the janitor nor expiry ever sees it: the photos stay on disk until the user deletes the folder by hand. Optional smallest fix: count skipped batches in `/health` and show a Settings row.
- **A corrupt `settings.json` silently resets to defaults.** The bad file is kept as `settings.json.corrupt` and the event is only logged; the UI does not say settings were reset, so a user may not notice that the notes-repo and extractor choices are gone.
- **A finished batch whose `delete_if` failed after a good push is never expired.** The push succeeded and a warning is logged, but the janitor ignores finished batches (`_action` returns `None` for `is_finished()`), so the folder stays until the user Discards it. The comment in `PushService._tidy_after_push` ("cleaned up by the next push or the janitor") is therefore too optimistic for the batch case; fixing it needs a source change, so it is left for a follow-up.
- **A crash or quit while an empty batch or a blank Kindle capture is open leaves it behind** until the 30-day expiry. Back-out cleanup only runs on deliberate Back / Prev / Next; Discard works.
- **The image route is O(open batches) per request.** `capture_image` still calls `_find` (so `store.list()` reads every `batch.json`) before the ETag 304 check. The 304 skips the photo read and decode, not that lookup. Smallest fix: resolve the capture id without listing, or check the ETag first from a cheap index.
- **A push retry after a bookkeeping failure reports 0 highlights / 0 files.** Correct, because the markers were already written and the retry only finishes the bookkeeping, but it reads oddly in the UI.
- **The `architecture-review.sh` and `code-review.sh` LLM stages need the `claude` CLI to be signed in again.** On 2026-11-22 the OAuth session had expired: the architecture LLM stage fails with `AUDIT_ERROR` (environmental, not a finding) and `code-review.sh` wrote only a placeholder. Until someone re-authenticates and re-runs both, the architecture hard gate is unverified beyond its static stage, and the code review rests on a manual review (findings M1, M2, m1-m9, mostly fixed in 7e9f1e5 and 410f11c).
- **Previews are generated lazily** on the first request for a photo, not pre-generated after upload. The first view of each photo pays one decode of the original (see RELIABILITY.md).

## Known limitations (accepted for v1)

- **Tesseract binary + photo-path e2e done (2026-11-22):** tesseract 5.5.1 on PATH; real-binary unit tests and OSD rotation tests pass; `scripts/ui-test.sh` photo-path Playwright e2e passed (synthetic yellow-highlight PNGs). Residual: yellow HSV range / kernel / two-column merge quality on the gitignored real GPS fixture photos is still un-tuned — optional polish if OCR misses highlights on phone photos. Keep those fixtures local for tuning.
- The photo `mtime` fallback for `captured_at` is the upload time (only EXIF gives the real photo time).
- A retry's requested extractor kind is forgotten if the extractor was unhealthy and the capture is re-queued; `extractor.concurrency` / `timeout_s` are read once at startup.
- A crash mid-write of a book file can leave a partial unmarked section at the tail; a retry appends a complete copy after it (the user can hand-fix).
- A highlight's *text* edited outside the app after it was written is not rewritten (highlights are recognised by id).
- Many small UI races (stale health fetch in Settings, `holdForPush` closure, Back double-click) are bounded and self-correcting; see the per-task notes in the git history.
